# 二创来源矩阵

**核心原则：GitHub 只是来源之一。** 文科用户如果只拿到 GitHub 链接，等于没有产出。
必须按学科轨道分流。

「二创」= 基于已有的公开作品/项目/数据，做出**属于你自己的、有增量的**成果。
这是在校生最快建立可信证据的方式：有基线可对比，有明确的技术/方法含量，
且工作量可控。

## 二、二创的四种模式

按「工作量 → 含金量」排序，让用户按时间预算选：

| 模式 | 做法 | 适用 | 工作量 |
| --- | --- | --- | --- |
| **A. 复现 + 对比** | 跑通原项目，换一个维度做对比实验 | 有 baseline 的算法/模型 | 中 |
| **B. 移植 + 适配** | 把它搬到新场景/新语言/新数据集 | 中文场景适配、垂直领域 | 中 |
| **C. 增强 + 贡献** | 加一个原项目没有的能力，提 PR | 想积累开源贡献 | 中高 |
| **D. 拆解 + 重写** | 读源码后自己实现一版精简版 | 深入理解原理，面试利器 | 低中 |

**文科对应**：
| 模式 | 做法 |
| --- | --- |
| A. 复刻 + 变体 | 用同样的选题-结构做一期你自己的内容，对比数据 |
| B. 移植 + 适配 | 把某行业的运营策略搬到另一行业做小规模验证 |
| C. 增强 + 沉淀 | 在已有案例基础上补一个量化复盘（原案例多半没数据） |
| D. 拆解 + 重写 | 拆解 10 个爆款，归纳出一套可复用的方法论并公开发表 |

**D 模式对文科尤其重要**：拆解 + 归纳本身就是研究能力，写成方法论文章发表，
既是作品也是能力证据。

## 三、每个二创推荐必须包含

```json
{
  "name": "owner/repo 或 案例名",
  "star": "92.0k",          // 或 "阅读 10w+"、"2024 年度案例"
  "lang": "Go/Python",      // 或 "深度报道"、"行业研报"
  "tag": "RAG+Agent 引擎",
  "why": "为什么这个值得二创（与 JD 的关联）",
  "fork": [
    "具体切入点 1（可执行，不是空话）",
    "具体切入点 2",
    "具体切入点 3"
  ],
  "mode": "A",              // 复现/移植/增强/拆解
  "accept": "验收标准：<可客观检验的完成标志>"
}
```

**`fork` 必须是可执行动作**，不能写「深入研究这个项目」。
反例：「学习它的架构」✅ 正例：「为它接入你自己的混合召回策略并做消融实验」。

## 四、合规红线（必须写进产出页面）

1. **遵守原仓库 License**（MIT/Apache 可商用，GPL 有传染性）
2. **注明 fork 来源与你的增量**
3. 简历标准写法：
   > 基于 `<项目名>`（附链接）二次开发，实现了 `<你的增量>`，`<量化效果>`
4. **不要直接抄代码当自己的**。面试一问细节就露馅，且涉及学术不端。
5. 文科引用案例/数据要注明出处，使用他人作品需符合著作权规定。

## 五、给用户的二创路线建议

按时间预算给出组合（写进第 5 步路线图）：

- **2 周**：D 模式 × 2（拆解重写）→ 快速积累面试可讲的细节
- **6 周**：D × 1 + A × 1 → 一个能讲原理，一个有实验数据
- **13 周**：D × 1 + A × 1 + C × 1（提一个真 PR）→ 完整证据链

**文科 13 周版**：
作品集上线 + 1 份完整研究报告 + 1 个真实运营数据的账号 + 1 篇公开方法论文章
