# 定制简历生成规则

## 零、第一原则：如实呈现

| 建议 | 说明 |
| --- | --- |
| 重排技能顺序、调整详略、改写措辞 | 让最相关的信息靠前 |
| 把用户已有经历**映射**到 JD 要求 | 换角度描述同一段经历 |
| 用 `[待补充：...]` 标出信息缺口 | 用户一眼看到还需要补什么 |
| 用 `【示例写法】` 给表达范式 | 帮助用户理解怎么写更好 |

**为什么建议如实**：HR 初筛靠关键词，但面试官会追问细节。一个说不清来源的数字，
在「这个 62%→81% 怎么测的？评测集多大？」的追问下很难自圆其说。

**执行方式**：生成的 HTML 里，`[待补充]` 渲染成**高亮**，
`【示例写法】` 渲染成**另一种高亮**，让用户一眼看到哪些需要自己回填或改写。

## 一、HR 筛选的真实机制

1. **机器初筛**：ATS/关键词匹配，看 JD 原词是否出现在简历里
2. **人工初筛（6–15 秒）**：只看**前 1/3 屏**——姓名、定位、技能栏、最近一段经历
3. **深度阅读**：只有初筛通过才看项目细节

→ 推论：**JD 原词必须出现在最显眼位置**。不要为了文采把「RAG」写成「检索增强生成」
（除非两个都写），不要为了排版把最强证据放到第二页。

## 二、生成步骤

### Step 1 · 抽关键词
从 `jd` 与 `req` 中抽出 10–15 个**名词性**关键词。分三档：
- **硬性**（req 前 3 条）：必须全部命中，否则简历会被机筛掉
- **工具类**：具体框架/软件/证书名
- **加分项**：req 里标「加分」「优先」的

### Step 2 · 技能矩阵重排
把用户的技能标签按「硬性 > 工具 > 加分 > 其他」排序。
每条技能后面**紧接着**放 JD 原词，并用 `<span class="hitmark">` 高亮。

格式：
```
{ k: "维度名", v: "技能1、技能2、JD原词【待补充：熟练度/年限】", hit: true }
```
`hit: true` 表示该条命中 JD；只有命中的才高亮。

### Step 3 · 经历映射
对每条 JD 要求，找用户已有经历中能作为证据的部分：

```json
["熟悉 RAG / Agent 架构", "技能栏第 1、2 项 + RAG 问答 Agent 项目"]
```

**找不到证据的条目**不要跳过，要显式写进缺口：
```json
["RL / Reward Model / 工具调用", "[待补充]：如做过 DPO / 奖励模型，务必单独列出"]
```
缺口清单本身就是给用户的行动指南——它直接变成第 3 步的 P0 项目。

### Step 4 · 项目排序
按与目标岗位的相关度**倒序**，最相关的放最上面。每个项目用四段式：

```
背景：为解决 <什么场景> 下的 <什么问题>
动作：构建/设计了 <具体技术或方法>，实现了 <关键机制>
结果：[待补充：量化结果，如 准确率 X%→Y%、耗时下降 Z%]
```

**「动作」段要写清技术取舍**，这是面试官最爱追问的地方：
不要写「使用了向量数据库」，要写「对比 Faiss 与 HNSWlib 后选择 X，因为 Y」。

### Step 5 · 摘要（Summary）
一句话定位 + 2–3 句最强证据。开头用轨道对应的定位模板（见 `track-dimensions.md`）。

格式：
```
[待补充] <专业>在读（<届别>），<核心能力1>，<核心能力2>。
[待补充：一句话量化最强成果，如"将某评测集准确率从 X% 提升到 Y%"]
```

## 三、写作规范

### 动词开头，去掉软性词
| 弱 | 强 |
| --- | --- |
| 参与了 | 主导 / 独立完成 / 从零搭建 |
| 负责了 | 设计了 / 实现了 / 优化了 |
| 协助完成 | （直接说自己做的那部分） |
| 学习能力强 | （用一个自学新框架做出 demo 的事实代替） |
| 沟通能力好 | （用协调 X 方、主导 X 场会议代替） |

### 量化优先
任何一条经历，问三个问题：
1. 规模多大？（数据量、用户数、字数、样本量、预算）
2. 变化多少？（提升/下降的百分比、倍数）
3. 多快？（耗时、周期、延迟）

答不上来 → `[待补充：规模/变化/耗时]`

### 长度
- 应届/实习：**严格 1 页**
- 社招：1–2 页

### 不同岗位版本必须真的不同
一稿多投是最常见的错误。差异化应体现在：
1. 技能栏顺序不同
2. 项目选择与排序不同
3. 摘要定位句不同
4. 同一项目在不同岗位下的**侧重描述不同**（做 Agent 岗就突出编排，
   做训练岗就突出数据处理与评测）

## 四、文理科的差异化写法

### 理工科
- 技术栈写具体版本/规模：「PyTorch、8×A100 训练、7B 模型 LoRA 微调」
- 指标写测试条件：「在 XX 评测集（200 条）上准确率 62%→81%」
- 链接必有：GitHub / 论文 / demo

### 人文社科
- **不许因为「不写代码」就写得虚**。把内容生产当工程写：
  「设计选题矩阵（5 大类 × 12 主题），周更 3 篇，6 个月累计 78 篇，总阅读 42 万，
   其中 5 篇 10w+，被 XX、XX 转载」
- 研究类写清方法：抽样方式、样本量、访谈轮次、编码方式
- 链接必有：作品集 / 报告 PDF / 发表链接
- 数据能力要显性化：哪怕只会 Excel 透视表和基础 SQL，也要写，并给 `[待补充：完成过什么数据项目]`

### 经管商科
- 写清分析框架与数据源：「用 PEST + 波特五力分析 X 行业，数据源为 XX 年报与 XX 研报」
- 模型写清假设与输出：「搭建 3 年财务预测模型，含敏感性分析，覆盖 5 个关键假设」
- 证书单列，标明已通过科目与分数

## 五、自检清单（生成后逐条过）

- [ ] 所有 `[待补充]` 都是用户确实没提供的信息，不是偷懒
- [ ] 没有任何一个数字、日期、公司名来自模型想象
- [ ] 硬性关键词（req 前 3 条）100% 出现在技能栏或经历里
- [ ] 技能栏第一条就是 JD 最看重的能力
- [ ] 最强证据在前 1/3 屏
- [ ] 每条项目都有量化结果的**位置**（哪怕是占位符）
- [ ] 动词开头，无「参与」「协助」「学习能力强」等软性词
- [ ] 不同岗位版本之间确实有实质差异
- [ ] 长度符合（应届 1 页）
